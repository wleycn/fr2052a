这是一个非常棒的架构升级思路！将 **Kafka** 和 **Iceberg** 引入后，你的项目将从一个传统的“关系型数据库批处理”架构，跃升为目前华尔街顶级投行正在大力转型的 **“现代流批一体数据湖仓（Lakehouse）”** 架构。

考虑到你是**单台服务器**且为了**演示目的**，我们需要对传统的重型 Hadoop 生态进行“轻量化”改造。

以下是如何将 Kafka + Iceberg 完美融入 FR 2052a 业务场景的完整设计方案。

---

### 一、 架构升级：为什么需要 Kafka + Iceberg？

在真实的投行场景中，FR 2052a 虽然是日终/月度报送，但其底层数据支撑需要解决两个痛点，这正是 Kafka 和 Iceberg 的价值所在：

1.  **Kafka 解决“实时性与解耦”**：核心银行系统（如贷款发放、大额存款进出）产生海量流水。用 Kafka 做 CDC（变更数据捕获）或事件流，可以**实时捕获流动性变化**，进行内部 T+0 流动性预警，而不是等 T+1 跑批才发现资金缺口。
2.  **Iceberg 解决“海量历史与批流一体”**：FR 2052a 经常需要回溯历史数据（如计算 30 天/90 天移动平均、压力测试）。Iceberg 提供了类似数据库的 ACID 事务、Time Travel（时间旅行）和 Schema 演进能力，完美替代笨重的传统 Hadoop (Hive/HDFS)。

#### 升级后的全景架构图

```text
[源系统: 核心银行/资金交易] 
       │ (实时交易流水 / CDC)
       ▼
┌─────────────────────────────────────┐
│  Kafka (KRaft 单节点, 无 ZK)        │ <-- 实时消息总线
│  Topics: core_txn, market_data      │
└──────────────┬──────────────────────┘
               │ (Spark Streaming / Flink 消费)
               ▼
┌─────────────────────────────────────┐
│  MinIO (S3兼容对象存储, 替代HDFS)   │ <-- 数据湖底座 (轻量级 Hadoop 替代)
│  └─ Iceberg Tables (Bronze/Silver)  │ <-- 开放表格式 (ACID, Time Travel)
└──────────────┬──────────────────────┘
               │ (Spark SQL / Trino / dbt 批量读取)
               ▼
┌─────────────────────────────────────┐
│  PostgreSQL (Gold / ADS 层)         │ <-- 轻量级结果存储，供报表和校验使用
│  └─ ads_fr2052a_report              │
└─────────────────────────────────────┘
```
*(注：强烈建议用 **MinIO** 替代传统的 Hadoop HDFS。MinIO 是 S3 兼容的轻量级对象存储，Iceberg 原生完美支持 S3，且单节点资源消耗极低，是现代 Lakehouse 的标准底座。)*

### 二、 业务场景映射：它们在 FR 2052a 中具体干什么？

#### 1. Kafka 的业务场景：实时流动性监控 & 数据入湖
*   **场景 A：大额资金异动实时预警 (Section C & F)**
    *   **业务逻辑**：当一笔超过 $50M 的批发存款（Wholesale Deposit）被提取，或者一笔巨额贷款被提取（Cash Outflow），Kafka 实时捕获该事件。
    *   **流处理**：Flink/Spark Streaming 消费 Kafka，实时更新当天的“预计净现金流”，如果触发 LCR（流动性覆盖率）红线，立即发送告警。
*   **场景 B：市场数据实时喂价 (Section G & H)**
    *   **业务逻辑**：证券组合（Section G）和衍生品（Section H）需要盯市（Mark-to-Market）。Kafka 接入 Bloomberg/Reuters 的实时汇率和证券价格流，持续更新 Iceberg 中的价格维度表。

#### 2. Iceberg 的业务场景：海量历史分析与数据修正
*   **场景 A：Time Travel（时间旅行）应对监管审计**
    *   **业务逻辑**：审计师质疑 9 月 1 日的 FR 2052a 报表中 Section B（回购）数据有误。由于数据存在 Iceberg 中，你可以直接查询 `SELECT * FROM iceberg_repos FOR TIMESTAMP AS OF '2026-09-01 23:59:59'`，**完美还原当时的数据快照**，而 PG 很难高效做到这一点。
*   **场景 B：Schema Evolution（模式演进）**
    *   **业务逻辑**：美联储突然在 FR 2052a 中增加了一个字段（如要求区分“央行数字货币存款”）。Iceberg 允许你直接在湖表上 `ALTER TABLE ADD COLUMN`，历史数据自动补 NULL，不会导致上游 ETL 崩溃。
*   **场景 C：海量历史压力测试 (Stress Testing)**
    *   **业务逻辑**：监管要求基于过去 3 年的所有交易流水进行流动性压力测试。3 年的明细数据（数亿行）放在 PG 中会导致查询极慢，而放在 Iceberg 中结合 Spark 可以高效进行分布式计算。

### 四、 数据流转代码实战 (Python + PySpark)

这是整个架构中最核心的部分：如何用代码把 Kafka、Iceberg 和 PG 串联起来。

#### 步骤 1：模拟数据写入 Kafka (Python Producer)
模拟核心银行系统不断产生存款交易流水。

```python
# producer.py: 模拟实时存款交易流入 Kafka
import json, time, random
from kafka import KafkaProducer

producer = KafkaProducer(
    bootstrap_servers='localhost:9092',
    value_serializer=lambda v: json.dumps(v).encode('utf-8')
)

while True:
    txn = {
        "txn_id": f"TXN-{random.randint(1000,9999)}",
        "account_id": f"ACC-{random.randint(1,50)}",
        "amount": round(random.uniform(10000, 5000000), 2), # 金额
        "currency": "USD",
        "txn_type": random.choice(["DEPOSIT", "WITHDRAWAL"]),
        "timestamp": int(time.time())
    }
    producer.send('core_banking_txns', value=txn)
    print(f"Sent: {txn}")
    time.sleep(1) # 每秒一条
```

#### 步骤 2：Spark Streaming 消费 Kafka 并写入 Iceberg (PySpark)
将实时流数据沉淀到数据湖的 Bronze 层（ODS）。

```python
# spark_streaming_to_iceberg.py
from pyspark.sql import SparkSession
from pyspark.sql.functions import from_json, col, to_timestamp
from pyspark.sql.types import StructType, StringType, DoubleType, LongType

# 初始化 Spark，加载 Iceberg 和 Kafka 依赖
spark = SparkSession.builder \
    .appName("FR2052a_Kafka_to_Iceberg") \
    .config("spark.jars.packages", "org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.5.0,org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.0") \
    .config("spark.sql.extensions", "org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions") \
    .config("spark.sql.catalog.lakehouse", "org.apache.iceberg.spark.SparkCatalog") \
    .config("spark.sql.catalog.lakehouse.type", "hadoop") \
    .config("spark.sql.catalog.lakehouse.warehouse", "s3a://fr2052a-bucket/warehouse") \
    .getOrCreate()

# 定义 Kafka 消息的 Schema
schema = StructType() \
    .add("txn_id", StringType()).add("account_id", StringType()) \
    .add("amount", DoubleType()).add("currency", StringType()) \
    .add("txn_type", StringType()).add("timestamp", LongType())

# 1. 读取 Kafka Stream
df_stream = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "localhost:9092") \
    .option("subscribe", "core_banking_txns") \
    .option("startingOffsets", "latest") \
    .load()

# 2. 解析 JSON 并转换时间戳
df_parsed = df_stream.select(from_json(col("value").cast("string"), schema).alias("data")) \
    .select("data.*") \
    .withColumn("txn_time", to_timestamp(col("timestamp")))

# 3. 写入 Iceberg 表 (Bronze 层 ODS)
# Iceberg 支持微批处理 (Micro-batch) 写入
query = df_parsed.writeStream \
    .format("iceberg") \
    .outputMode("append") \
    .option("checkpointLocation", "/tmp/checkpoints/txns") \
    .option("path", "lakehouse.bronze.ods_deposits_stream") \
    .trigger(processingTime='10 seconds') \
    .start()

query.awaitTermination()
```

#### 步骤 3：dbt + Spark 批量处理 Iceberg (OWD -> OWS)
在 Airflow 的调度下，每天凌晨使用 dbt 连接 Spark，对 Iceberg 中的海量数据进行清洗和聚合。

```sql
-- dbt/models/intermediate/ows_funding_summary.sql
-- dbt 配置使用 Spark 适配器连接 Iceberg
{{ config(materialized='table', file_format='iceberg', location='s3a://fr2052a-bucket/warehouse/silver/ows_funding_summary') }}

WITH daily_agg AS (
    SELECT 
        date_trunc('day', txn_time) AS report_date,
        account_id,
        SUM(CASE WHEN txn_type = 'DEPOSIT' THEN amount ELSE 0 END) AS total_inflow,
        SUM(CASE WHEN txn_type = 'WITHDRAWAL' THEN amount ELSE 0 END) AS total_outflow
    FROM {{ source('lakehouse_bronze', 'ods_deposits_stream') }}
    WHERE txn_time >= current_date() - interval 1 day
    GROUP BY 1, 2
)
SELECT * FROM daily_agg
```

#### 步骤 4：将最终结果导出到 PostgreSQL (ADS 层)
Iceberg 适合海量计算，但不适合高并发的 BI 报表查询。因此，最后一步是将聚合好的 ADS 结果推送到 PG。

```python
# export_to_postgres.py (Airflow PythonOperator)
from pyspark.sql import SparkSession

spark = SparkSession.builder...getOrCreate()

# 读取 Iceberg 中的最终报表数据
df_ads = spark.read.format("iceberg").load("lakehouse.gold.ads_fr2052a_report")

# 写入 PostgreSQL
df_ads.write \
    .format("jdbc") \
    .option("url", "jdbc:postgresql://postgres:5432/fr2052a") \
    .option("dbtable", "ads_fr2052a_report") \
    .option("user", "fr2052a") \
    .option("password", "secret") \
    .mode("overwrite") \
    .save()
```

### 五、 单服务器资源分配与避坑指南

在单台机器上跑这么多组件，**资源管理**是成败的关键。

| 组件 | 建议分配内存 (JVM/Container) | 核心作用 | 避坑指南 |
| :--- | :--- | :--- | :--- |
| **Kafka** | 1 GB | 消息缓冲 | 必须用 KRaft 模式，**绝对不要装 Zookeeper**，省一半内存。 |
| **MinIO** | 512 MB | 对象存储 | 替代 HDFS。HDFS 的 NameNode+DataNode 至少吃掉 2-3GB 内存且启动极慢。 |
| **Spark (Master+Worker)** | 4 - 6 GB | 计算引擎 | 限制 Worker 的 core 和 memory (`SPARK_WORKER_MEMORY=4g`)，防止 OOM 把机器卡死。 |
| **PostgreSQL** | 1 GB | ADS & 元数据 | 仅存储最终报表结果和 Airflow/dbt 元数据，不存明细。 |
| **Airflow** | 2 GB | 调度 | 使用 `LocalExecutor` 或 `SequentialExecutor`，不要用 Celery/Kubernetes。 |
| **OS & 其他** | 2 - 3 GB | 系统开销 | 预留足够的 Swap 空间以防万一。 |

**总内存需求**：建议服务器至少具备 **16GB RAM**（推荐 32GB）。如果是 8GB 的笔记本，建议去掉 Spark，改用 **DuckDB** 作为轻量级计算引擎来读写 Iceberg（DuckDB 对 Iceberg 的支持非常好，且内存占用极小）。

### 改进一：缺失了监管报表的灵魂 —— “总账对账机制 (GL Reconciliation)”

**🔴 原设计的盲点：**
原设计保证了数据从 ODS 到 ADS 的转换正确性（通过 dbt tests 和 GE），但忽略了一个致命问题：**如果源系统（如核心存款系统）本身的数据就是错的，或者漏推了数据怎么办？** 
在真实的 FR 2052a 报送中，如果 ADS 层算出的负债总额与银行财务总账（General Ledger, GL）对不上，报表会被监管直接打回，甚至引发合规调查。

**🟢 改进方案：引入 Sub-ledger to GL 对账层**
在 OWS 和 ADS 之间，或者在 ADS 生成后，必须增加一个强制的对账环节。

```sql
-- dbt/models/marts/reconciliation/rec_gl_vs_liquidity.sql
{{ config(materialized='table', tags=['reconciliation', 'critical']) }}

WITH gl_totals AS (
    -- 从财务总账系统获取的当日科目余额
    SELECT report_date, gl_account_id, debit_balance, credit_balance 
    FROM {{ source('finance', 'daily_gl_balances') }}
    WHERE gl_account_id IN ('2001', '2002') -- 存款和借款类科目
),

liquidity_totals AS (
    -- 从 FR 2052a 数据模型汇总的金额
    SELECT report_date, 
           SUM(liability_amount_usd) as total_liability
    FROM {{ ref('ows_funding_summary') }}
    GROUP BY 1
)

SELECT 
    l.report_date,
    g.credit_balance AS gl_amount,
    l.total_liability AS fr2052a_amount,
    (g.credit_balance - l.total_liability) AS variance, -- 差异额
    CASE WHEN ABS(g.credit_balance - l.total_liability) < 0.01 THEN 'PASS' ELSE 'FAIL' END AS status
FROM liquidity_totals l
JOIN gl_totals g ON l.report_date = g.report_date
```
**价值**：在演示时，展示这个对账表并说明“如果 variance 不为 0，Airflow 会阻断报送并触发告警”，会让懂行的面试官/审计师对你刮目相看。

### 改进二：缺乏对“迟到数据”与“报表重述 (Restatement)”的处理机制

**🔴 原设计的盲点：**
原假设是每天凌晨 2 点，所有 T-1 日的数据都整齐地躺在 ODS 里。但现实中，场外衍生品（OTC Derivatives）结算、跨境汇款等数据经常会**迟到（Late Arriving Data）**，甚至在 T+3 才发现 T-1 的某笔交易金额录错了。监管允许并在某些情况下要求对历史报表进行**重述（Restatement）**。

**🟢 改进方案：引入 Watermark 与 重述工作流**
1. **数据模型改进**：在 Iceberg/PG 表中强制加入 `etl_load_timestamp` 和 `is_latest_version` 字段。使用 **SCD Type 2（缓慢变化维）** 记录数据变更历史。
2. **Airflow 流程改进**：设计一个专门的 `backfill_and_restate` DAG。当发现 9 月 1 日数据有误时，不是直接 UPDATE，而是插入新版本，并自动触发 9 月 1 日及之后所有受影响日期的 dbt 重跑和 GE 重新校验。

```sql
-- Iceberg / PG 中的 SCD2 设计
SELECT 
    facility_id,
    outstanding_amount,
    valid_from_date,
    valid_to_date,       -- 9999-12-31 表示当前有效
    is_current_flag,     -- Y / N
    last_modified_reason -- 'LATE_ARRIVAL' / 'CORRECTION' / 'ORIGINAL'
FROM owd_loans
```

### 改进三：过度设计 (Over-engineering) 导致演示失焦

**🔴 原设计的盲点：**
我们之前引入了 Kafka + Spark + Iceberg + MinIO + Airflow + dbt + GE + DataHub + PG。对于单台服务器的演示项目来说，这个技术栈**太重了**。
如果服务器宕机、Kafka OOM、Spark 报错，你将花费 80% 的时间在修基础设施，而不是展示 FR 2052a 的业务逻辑。监管人员或业务面试官其实并不关心你的 Kafka 是怎么部署的。

**🟢 改进方案：采用“双轨制”架构（Core + Advanced）**
将项目拆分为两个清晰的模块：

1. **Core 核心演示版（必须 100% 稳定运行，纯批处理）**：
   - **栈**：PostgreSQL + dbt + Great Expectations + Airflow (LocalExecutor)
   - **重点**：展示复杂的 FR 2052a 数据模型（到期分桶、HQLA 分类）、GL 对账、GE 合规校验、Airflow 调度。
   - **数据量**：10 万 - 100 万行，PG 完全能秒级响应。

2. **Advanced 扩展版（按需启动，展示技术深度）**：
   - **栈**：Kafka + MinIO(Iceberg) + Spark
   - **重点**：展示当数据量达到亿级时，如何利用 Lakehouse 进行 Time Travel 审计和实时流动性预警。
   - **策略**：在演示时，Core 版做 Live Demo（实操），Advanced 版通过架构图和预先录制好的 Jupyter Notebook 结果来讲解。

---

### 改进四：数据血缘缺乏“业务解释性” (Business Lineage)

**🔴 原设计的盲点：**
DataHub 和 dbt docs 能生成极好的**技术血缘**（Table A -> Table B -> Table C）。但是，当美联储审查员问：“你们 Section G 的 HQLA Level 1 资产市值，具体套用了哪条监管规则？折算系数（Haircut）是怎么定的？” 技术血缘回答不了这个问题。

**🟢 改进方案：在 dbt 中引入“监管规则映射 (Regulatory Mapping)”**
在 dbt 的 `schema.yml` 中，利用自定义属性（Meta）将数据字段与 FR 2052a 的官方 PDF 说明书（Instructions）强绑定。

```yaml
# models/marts/ads_fr2052a_sec_g.yml
models:
  - name: ads_fr2052a_sec_g_hqla
    description: "FR 2052a Section G: HQLA (High-Quality Liquid Assets)"
    meta:
      regulatory_reference: "FR 2052a Instructions Page 42, Section G"
      owner: "Treasury Liquidity Team"
    columns:
      - name: hqla_level_1_mv_usd
        description: "Level 1 HQLA Market Value in USD"
        meta:
```

### 改进五：忽视了 PII 数据脱敏与行列级权限控制

**🔴 原设计的盲点：**
FR 2052a 的底层明细数据（OWD 层）包含大量客户账号、交易对手名称（如对冲基金、大型企业），属于高度敏感的 PII/机密数据。原设计直接让数据流向 ADS，没有安全拦截。

**🟢 改进方案：在 OWD 层实施动态数据脱敏 (Dynamic Data Masking)**
利用 PostgreSQL 的 Security Barrier Views 或 dbt 的宏，对敏感字段进行脱敏，确保只有特定角色（如合规官）才能看到明文。

```sql
-- dbt/macros/masking.sql
{% macro mask_pii(column_name) %}
    CASE 
        WHEN current_user IN ('compliance_officer', 'fr2052a_admin') 
        THEN {{ column_name }}
        ELSE '***-***-' || RIGHT({{ column_name }}, 4)
    END
{% endmacro %}

-- 在 stg_deposits.sql 中使用
SELECT
    {{ mask_pii('account_number') }} AS account_number,
    principal_amount_usd,
    ...
```

**2. GL 对账模型 (`rec_gl_vs_liquidity.sql`)**
```sql
{{ config(materialized='table', tags=['reconciliation', 'critical']) }}

WITH gl_totals AS (
    -- 模拟从总账获取的数据
    SELECT current_date as report_date, '2001' as gl_account_id, 150000000.00 as credit_balance 
),
liquidity_totals AS (
    -- 从 FR 2052a 模型汇总
    SELECT current_date as report_date, SUM(amount_usd) as total_liability
    FROM {{ ref('ows_deposits') }} -- 假设这是你的存款汇总模型
)
SELECT 
    l.report_date,
    g.credit_balance AS gl_amount,
    l.total_liability AS fr2052a_amount,
    (g.credit_balance - l.total_liability) AS variance,
    CASE WHEN ABS(g.credit_balance - l.total_liability) < 0.01 THEN 'PASS' ELSE 'FAIL' END AS status
FROM liquidity_totals l CROSS JOIN gl_totals g
```

#### 改进 2：迟到数据与重述 (Iceberg + Spark)

在 Server 2 上创建一个 PySpark 脚本 `process_iceberg_late_data.py`，展示如何处理迟到数据并利用 Iceberg 的 Time Travel。

```python
from pyspark.sql import SparkSession

# 连接 Server 1 的 MinIO 和 Server 2 的 Spark
spark = SparkSession.builder \
    .appName("FR2052a_Iceberg_Restatement") \
    .config("spark.jars.packages", "org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.5.0,org.apache.hadoop:hadoop-aws:3.3.4") \
    .config("spark.sql.extensions", "org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions") \
    .config("spark.sql.catalog.lakehouse", "org.apache.iceberg.spark.SparkCatalog") \
    .config("spark.sql.catalog.lakehouse.type", "hadoop") \
    .config("spark.sql.catalog.lakehouse.warehouse", "s3a://fr2052a-bucket/warehouse") \
    .config("spark.sql.catalog.lakehouse.s3.endpoint", "http://192.168.1.10:9000") \
    .config("spark.sql.catalog.lakehouse.s3.access-key", "admin") \
    .config("spark.sql.catalog.lakehouse.s3.secret-key", "password123") \
    .config("spark.sql.catalog.lakehouse.s3.path-style-access", "true") \
    .getOrCreate()

# 1. 创建 Iceberg 表 (支持 Schema 演进)
spark.sql("""
    CREATE TABLE IF NOT EXISTS lakehouse.bronze.ods_deposits (
        txn_id STRING, account_id STRING, amount DOUBLE, txn_date DATE
    ) USING iceberg
    PARTITIONED BY (txn_date)
""")

# 2. 模拟 T-1 日数据
df_t1 = spark.createDataFrame([("TXN001", "ACC1", 10000.0, "2026-09-15")], ["txn_id", "account_id", "amount", "txn_date"])
df_t1.writeTo("lakehouse.bronze.ods_deposits").append()

# 3. 模拟 T+2 日发现 T-1 日数据有误，进行重述 (Restatement)
# 先删除错误数据 (Iceberg 支持 ACID 删除)
spark.sql("DELETE FROM lakehouse.bronze.ods_deposits WHERE txn_id = 'TXN001'")

# 插入修正后的数据
df_t1_corrected = spark.createDataFrame([("TXN001", "ACC1", 10500.0, "2026-09-15")], ["txn_id", "account_id", "amount", "txn_date"])
df_t1_corrected.writeTo("lakehouse.bronze.ods_deposits").append()

# 4. 审计师审查：使用 Time Travel 查看修正前的数据快照
print("--- 历史快照 (修正前) ---")
spark.read.option("as-of-timestamp", "1726444800000").table("lakehouse.bronze.ods_deposits").show() # 替换为实际时间戳
```

| 报送闭环 | ADS 后缺少 XBRL/XML/CSV 生成与回执 | 增加报送文件生成、校验、提交、回执状态 |
| 运维保障 | 缺少备份、监控、SLA、容灾 | 增加 PG dump、MinIO 版本、Iceberg snapshot、Prometheus/Grafana |
| 双机部署 | 端口、网络、MinIO endpoint 易错 | 明确 Server1/Server2 角色、端口、启动顺序、避坑 |

## 0.3 总体判断

原草稿是一个优秀的“现代数据工程模板”，但还不是完整的“监管科技解决方案”。  
本项目最终应定义为：

> **一个以 FR 2052a 为核心，具备流批一体、监管规则映射、GL 对账、重述审计、数据脱敏、数据质量闭环的双机 Lakehouse 演示项目。**
