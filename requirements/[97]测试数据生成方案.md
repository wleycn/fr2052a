你的方案**非常好**，而且比“PySpark 直接写 Iceberg”更贴近真实企业架构。下面先给出评估，再给你完整的 CSV 生成脚本。

---

## 一、方案评估：为什么这样设计好

| 维度 | 你的方案 | 评价 |
|---|---|---|
| 数据特征匹配 | 交易数据高频、实时；Reference 低频、稳定 | ✅ 完全符合 |
| 架构真实度 | 交易走 Kafka，Reference 走批 | ✅ 与投行生产环境一致 |
| 可重放性 | CSV 落地，可重复回放 | ✅ 适合演示与测试 |
| 解耦 | 生成与入湖解耦，你自己控制后续 | ✅ 灵活 |
| 审计友好 | CSV 可留档，可对比 | ✅ 监管场景友好 |
| Kafka 价值体现 | 交易数据有实时性 | ✅ 不浪费 Kafka |
| Iceberg 统一存储 | 两条路径最终都进 Iceberg | ✅ 流批一体 |
| 复杂度 | 比全 PySpark 方案略高，但可控 | ✅ 值得 |

**唯一需要注意的点：**

1. **交易数据 CSV 里要有 `event_time` 字段**，便于 Kafka Producer 按时间重放。
2. **交易数据的 Kafka Topic 分配要清晰**：存款、回购、贷款、证券、衍生品、GL、表外，可以按 Topic 分，也可以合并到 `fr2052a_transactions` 一个 Topic 用 `event_type` 区分。
3. **Reference 数据入 Iceberg 时要有幂等策略**（例如 `overwrite` 或 `merge`），否则重复跑会翻倍。
4. **ODS 交易数据引用的币种、交易对手、实体，必须与 REF CSV 一致**，我下面的脚本会保证这一点。

            holiday = "Labor Day"
        elif d == date(2026, 11, 26):
            is_business = False
            holiday = "Thanksgiving"
        elif d == date(2026, 12, 25):
            is_business = False
            holiday = "Christmas"
        rows.append((d.isoformat(), is_business, holiday, "US"))

    header = ["calendar_date", "is_business_day", "holiday_name", "jurisdiction"]

## 六、后续流程建议（由你自己处理）

### 1. REF 数据：批处理入 Iceberg

```text
ref/*.csv
  → Spark / dbt seed / PySpark
  → Iceberg: lakehouse.ref.ref_*
```

建议：
- 使用 `overwrite` 或 `merge` 保证幂等；
- 每次跑批前清空对应表或按主键 upsert；
- 可以先用 dbt seed 加载小数据，大数据用 Spark。

### 2. ODS 交易数据：Kafka 实时流入 Iceberg

```text
ods/*.csv
  → Kafka Producer 逐行读取 CSV
  → Kafka Topic: fr2052a_transactions（或按业务分 Topic）
  → Spark Streaming 消费
  → Iceberg: lakehouse.bronze.ods_*
```

建议：
- Kafka Producer 读取 CSV 时，把 `event_time` 作为消息时间戳；
- 可以按 `source_system` 分 Topic：
  - `fr2052a.core_banking`
  - `fr2052a.treasury`
  - `fr2052a.loan`
  - `fr2052a.custody`
  - `fr2052a.derivatives`
  - `fr2052a.finance`
  - `fr2052a.off_bs`
- 或者统一一个 Topic：`fr2052a_transactions`，用 `event_type` 字段区分。
- Spark Streaming 写入 Iceberg 时按 `event_time` 分区，便于 Time Travel。

### 3. 一致性保障

- ODS 的 `currency` 全部来自 REF 的 `ref_exchange_rates`；
- ODS 的 `counterparty_id` / `borrower_id` / `issuer_id` 全部来自 REF 的 `ref_counterparty`；
- ODS 的 `branch_code` 前缀 `BR-` 后接 `entity_code`，来自 REF 的 `ref_entity_hierarchy`；
- ODS 的所有日期落在 REF 的 `ref_calendar` 范围内。

这样，你后续不管是走 Kafka 还是批处理，数据都能对齐，不会出现“ODS 引用了不存在的交易对手”这类问题。

## 七、总结

你的方案是**最佳实践**：

- **REF 走批处理**：低频、稳定、可幂等。
- **交易数据走 Kafka**：高频、实时、可重放。
- **CSV 作为中间落地**：可审计、可回放、可对比。
- **最终都进 Iceberg**：流批一体，统一存储。

上面的脚本可以直接用，后续 Kafka Producer、Spark Streaming、dbt/Spark 入 Iceberg 的部分你自己控制，完全符合你“我自己来处理后续流程”的需求。
